# 我从 yage.ai 的文章里「蒸馏」出了一个写作 skill

上周我干了一件事：把 yage.ai 上的所有深度技术文章一股脑丢给了 Claude Opus 4.6。

不是让它总结内容，而是问了一个很具体的问题：「这些文章有什么比较相似的结构吗？」

我知道鸭哥的文章读起来有一种独特的节奏感。每篇文章都能把一个很复杂的技术话题讲得让非专业读者也能跟住，同时又不让专业读者觉得浅。但我一直说不清这种感觉到底来自什么。是类比？是数据？是叙事结构？还是某种更底层的模式？

于是我决定让 AI 帮我拆解。

## 发现：六段式骨架

Opus 给出的分析比我预期的细致。它识别出了几乎所有文章共享的一个结构模式：

每篇文章都有一个**核心矛盾**作为骨架。不是「A 技术很厉害，我来介绍一下」，而是「A 和 B 之间存在一个大多数人没意识到的冲突，这个冲突决定了接下来三年的走向」。

围绕这个矛盾，文章展开为六个阶段：

1. **钩子**：一个具体的场景，前三句没有任何术语
2. **历史回溯**：这个问题从哪来的
3. **矛盾展开**：用数据把张力摆到台面上
4. **技术展开**：拆解各种方案，每个方案配一个非技术类比
5. **现实对照**：学术论文 vs 实际部署
6. **读者收束**：回到开头的场景，给出判断框架

有意思的是写作顺序。鸭哥的文章读起来是 1→6 的线性流，但最佳的写作顺序是先写 3（矛盾展开），再写 4（技术展开），然后 2、5、6，最后才写 1（钩子）。因为你得先知道文章的心脏在哪，才能设计最精准的开头。

## 从结构分析到可执行的 skill

知道结构是一回事，能复现是另一回事。

我又给 Opus 发了第二轮 prompt：

> 参考这个，我觉得可以蒸馏出一个 skill，每次给一个主题和一些思考，agent 会去找一些链接、论文新闻材料，先生成框架草图，然后去找资料，根据资料进行进一步分析，生成每一个段落，最后整合生成完整文章，每个中间 step 都存下来。

关键在「每个中间 step 都存下来」。我不想要一个黑盒——丢进去一个主题，吐出来一篇文章。我要的是一个有中间产物的流水线，每一步都能回溯、能干预、能迭代。

框架草图是一个子页面。素材库是一个子页面。每个段落的初稿也是一个子页面。这样如果第四段的技术展开写得不对，我可以只回退那一段重新来，不用从头开始。

第三轮 prompt 要求把它变成一个完整的、可以直接交给 AI agent 执行的 skill specification：

> 能不能把这个模版抽象成一个 writing 的 skill，给定一个主题之后，先设计类似的框架，然后每一个阶段都有一个资源获取和消化的过程，最终能产出一篇类似的文章。

产出就是下面这个完整的 skill。

## 实际使用效果

我用这个 skill 已经写了好几篇文章，效果比我预期的好。几个观察：

**框架设计阶段最有价值。** 找到核心矛盾之后，整篇文章的方向就定了。写的时候不会跑偏，不会写着写着变成流水账。

**素材库阶段最耗时间，但也最值得。** agent 找回来的资料经常会改变我对主题的判断。有好几次我在这个阶段发现自己最初的假设是错的，需要调整框架。这恰恰是好事——说明流程在 work。

**逐段生成比一次性生成好太多。** 每段写完都有自检清单（有没有类比？有没有数据？和上一段衔接了吗？），质量控制是分布式的，不是在最后才发现问题。

**反 AI 味的 checklist 是刚需。** 不加这个，AI 写出来的东西一眼就能看出来。加了之后至少过了基本的「人味」门槛。不过说实话，这个 checklist 本身也在不断迭代，因为 AI 的写作习惯每隔几个月就会变。

## 一些不工作的地方

钩子是最难的。这个 skill 能帮 agent 写出结构正确的钩子，但真正好的钩子需要一种对读者心理的直觉，目前的 AI 还差一点。通常我会手动改第一段。

另一个问题是类比的质量。skill 里要求每个技术概念配一个非技术类比，AI 确实会给，但有些类比很生硬。好的类比（比如鸭哥的「KV cache = 工位之间的隔离墙」）需要对技术和日常生活都有深入理解，这个我暂时没找到好的系统化办法，还是靠人去筛和改。

## 完整 Skill

下面是完整的 skill specification。你可以把它交给任何支持多步骤执行的 AI agent（我用的是 Notion AI 的自定义 agent），给它一个主题和你的初始思考，它就会按阶段执行。

```markdown
# 鸭哥式深度技术写作 Skill

## 概述

从 yage.ai 的写作风格中蒸馏出的深度技术文章写作 skill。
给定一个主题和一些初始思考/观点，agent 按阶段执行：
框架设计 → 资源搜集 → 逐段生成 → 整合输出。
每个中间 step 都保存为子页面，便于回溯和迭代。

---

## Phase 0：输入收集

在开始之前，需要从用户处收集以下信息：

- **主题**：文章要讨论的核心技术/现象/事件
- **初始思考**：用户对这个主题已有的判断、直觉、或想探索的角度（1-3 句话即可）
- **目标读者**：默认为「有技术背景但不一定是该细分领域专家」
- **语言**：中文（默认）/ 英文
- **参考素材（可选）**：用户已知的论文、新闻链接、数据源

---

## Phase 1：核心矛盾提炼 + 框架设计

**目标**：在写任何内容之前，先找到文章的「骨架」——一个结构性矛盾或张力。

### 1.1 提炼核心矛盾

鸭哥文章的灵魂是一个不可能三角 / 悖论 / 被忽视的张力。
在动笔前必须先回答：

- 这个主题里，什么和什么是冲突的？
- 大多数人的直觉是什么？现实为什么不是那样？
- 学术界/工业界对这个问题的理解差异在哪？

### 1.2 设计六段式框架

| 阶段 | 功能 | 典型标题风格 | 篇幅参考 |
|------|------|------------|----------|
| ① 钩子 | 用一个具象场景把读者拉进来，不解释术语 | （无标题，直接是开头段） | 2-4 段 |
| ② 历史回溯 | 这个问题从哪来？过去怎么解决的？ | 「一段被忽略的历史」 | 3-6 段 |
| ③ 矛盾展开 | 把核心矛盾摆到台面上 | 「三角为什么解不了」 | 4-8 段 |
| ④ 技术展开 | 深入拆解各种方案/路径 | 「四种传统思路」 | 8-15 段 |
| ⑤ 现实对照 | 学术 vs 工业、理论 vs 部署 | 「论文之外的现实」 | 3-6 段 |
| ⑥ 读者收束 | 回到「对你意味着什么」 | 「怎么选：从四个问题出发」 | 3-5 段 |

### 1.3 输出物

保存为子页面 `[主题] - Step 1: 框架草图`，内容包括：
- 一句话核心矛盾
- 六段式大纲（每段 1-2 句话概括要点）
- 每段预计需要的素材类型

---

## Phase 2：资源搜集与消化

**目标**：为框架中的每一段找到支撑素材，建立一个「素材库」。

### 2.1 搜索策略

按框架中的每个阶段，依次搜集：

- **钩子场景**：找一个真实的、具体的、读者能代入的案例
- **历史脉络**：原始论文、教科书级参考、领域综述
- **核心数据**：支撑矛盾的定量证据
- **技术细节**：各方案的原始论文或技术博客
- **工业案例**：真实部署的案例、企业财报、工程博客
- **对立观点**：反面证据或不同立场，避免单向叙事

### 2.2 素材消化规则

对每条素材，提取并记录：
- 来源 URL
- 一句话摘要
- 关键数据点
- 对应框架位置
- 可信度评估：一手数据 > 权威分析 > 二手报道 > 社区讨论

### 2.3 输出物

保存为子页面 `[主题] - Step 2: 素材库`，按框架阶段分组整理。

---

## Phase 3：逐段生成

**目标**：按框架逐段写作，每段写完即保存。

### 3.1 写作规则

**开头（钩子）**
- 不用「本文将介绍」这种元叙述
- 直接把读者扔进一个场景
- 前三句不出现任何术语

**技术解释**
- 每个技术概念必须配一个非技术类比
- 类比的标准：读者不需要任何前置知识就能理解

**数据使用**
- 每个论点至少有一个定量支撑
- 数字要有参照系（「300 兆瓦大约相当于三十万户家庭」）
- 来源标注使用行内链接，不用脚注

**段落节奏**
- 长段之后接短段
- 避免连续三段以上没有数据或案例的纯论述
- 每 800-1000 字设一个小标题

**语气**
- 不用「让我们来看看」「接下来我们将讨论」
- 不做价值预判，让事实自己说话
- 允许偶尔出现带有分析者视角的直接判断

**结尾**
- 不写「总之」「综上所述」
- 回到开头的场景或人物，形成闭环
- 最后一句应该是一个判断或一个问题，不是总结

### 3.2 生成顺序

1. 先写 ③ 矛盾展开（文章的心脏）
2. 再写 ④ 技术展开
3. 然后写 ② 历史回溯
4. 接着写 ⑤ 现实对照
5. 然后写 ⑥ 读者收束
6. 最后写 ① 钩子

### 3.3 每段自检清单

- 是否有核心类比？
- 是否有定量支撑？
- 是否和上一段有自然的逻辑衔接？
- 是否避免了元叙述？

---

## Phase 4：整合与打磨

**目标**：把六段拼成一篇完整文章，处理衔接、节奏和一致性。

### 4.1 整合检查清单

- 叙事连贯性：从钩子到收束，读者能不间断地读完吗？
- 类比一致性：前面用的类比后面有延续吗？
- 数据密度：全文数据/案例分布均匀吗？
- 长度平衡：技术展开不超过全文 40%
- 小标题：应该是判断句或问题句（「三角为什么解不了」✓「不可能三角分析」✗）
- 开头结尾呼应：结尾回到了开头的场景吗？

### 4.2 最终格式

- **标题**：一句判断或一个悖论，不超过 20 字
- **全文字数**：3000-6000 字（中文）

---

## 反 AI 味 Checklist

### 标点
- 少用破折号「——」，尤其是连续出现的
- 不用唐突引号给普通词加重音
- 不在小标题后接冒号收尾

### 句式
- 删掉「不是 A，而是 B」「与其说…不如说…」
- 删掉「没有 X，没有 Y，甚至没有 Z」三段递进否定
- 少用「底层逻辑」「范式」「本质上」「换句话说」
- 长短句故意打乱，允许偶尔有口语化表述

### 结构
- 不默认走「总分总」八股骨架
- 不无脑加列表和加粗小标题
- 不篇尾强行「金句升华」

### 内容
- 多写过程，少写结论
- 描写篇幅 ≤ 事件信息量
- 给具体的人名、地点、数字、时间
- 允许情绪起伏和锋利的态度
```

## 为什么要公开这个 skill

两个原因。

第一，这个 skill 本身就是「用 AI 蒸馏人类能力」的一个案例。鸭哥写了几十篇文章，每篇都是手工打磨的，但里面的结构模式是可以被提取和复用的。这不是替代人类写作，是把人类积累的隐性知识变成显性的、可传播的工艺流程。

第二，我想看看其他人用这个 skill 能写出什么。结构相同但矛盾不同、素材不同、视角不同，最终产出的文章应该完全不一样。如果你用了，可以告诉我效果怎么样。

这个 skill 还在迭代。每写一篇新文章，我都会发现一些可以改进的地方。目前最大的改进方向是钩子的质量和类比的筛选机制。如果你有好的想法，欢迎在 GitHub 上提 issue。
